# Threads daily editorial cycle (development, opt-in)

The existing three JST slots become one coherent daily theme: 07:30 reader-first column, 12:30 selection checklist/comparison, 19:30 related PR. The PR preserves the official affiliate URL exactly. No isolated PR fallback. The daily commander builds a proposal from official Rakuten discovery and bounded detail/page research; the selection uses available audited item performance and excludes recently featured products. Missing evidence holds the cycle. Night evaluation records confirmed stages and measured per-post views by ID; missing data and campaign-level affiliate attribution stay unknown.

`CFE_THREADS_DAILY_CYCLE_ENABLED=true` opts into manual batch review; default off. Existing auto-post and reply settings remain separate. Review locally from the agent directory with `node --env-file=.env src/review-threads-daily-cycle.js`; owner approval of the exact digest uses `node --env-file=.env src/review-threads-daily-cycle.js --approve <digest>`. This command does not publish or approve external replies. Replies require a separately reviewed exact URL list in the approval document, unchanged source/draft, confirmed morning stage, existing reply enable flag and daily limit of three. Missing approvals hold. No catch-up or uncertain retry; earlier stages must be officially confirmed before progression. No automatic new tracking ID generation or invented attribution.

No production configuration or live publication is performed merely by installing this release. M8 live end-to-end verification is still required. This cycle does not implement note/ROOM features or image publishing.

Tests: `node --test test/threads-daily-cycle.test.js test/threads-daily-preparation.test.js` (mocked APIs, no live calls).

## Pre-activation check

Run from the installed M8 agent directory with the existing environment: `node --env-file=.env src/preview-threads-daily-cycle.js --read-only-research`. This bounded Rakuten-only research prints redacted sample copy and the closed publication gate. It writes neither a proposal nor an approval, does not access Threads or change services, and returns exit 2 when evidence is insufficient. It must not be treated as a live publication test. Actual approval to install/change the production runtime, code deployment, and verification of the first approved three-slot sequence are separate. Keep the current running version unchanged until that approval; enable the opt-in only after an approved installation and a successful read-only rehearsal. Rollback is disabling the opt-in and returning to the prior approved revision through the existing deployment process.

## Owner-authorized recurring own-account publishing

After deployment and successful real-data rehearsal, the owner may run `node --env-file=.env src/activate-threads-daily-cycle.js --activate` on M8. It verifies the current local health, exact account `rakumitsu_select`, three slots, existing posting enabled, and external replies disabled. It writes only `.data/threads-daily-owner-policy.json`, which is read by both the core and daily commander without a restart. It does not itself submit posts. The daily commander at 06:30 prepares each day's plan. The standing policy accepts only a same-day immutable three-stage plan with two or more distinct literal facts, validated item/affiliate identity, fresh evidence, full editorial gate score, and exact regenerated copy. The 3/day cap and sequence confirmation are unchanged. No external reply approval is inferred. The local `--pause` action disables automatic authorization without reverting to legacy isolated PRs. A malformed retained file also fails closed. No post is replayed after a missed slot. For verification, `/health` exposes `dailyCycleEnabled` and `dailyAutoPublishEnabled`; night evaluation reports actual confirmed stages.
### Product-independent fallback (proposed, separate owner opt-in)

If bounded research cannot establish a qualified product, prepare a three-slot editorial-only plan from curated lifestyle guides. No affiliate URL, product claim, external reply suggestion or PR is permitted in this plan. Rotate themes and avoid exact copy used in the last five days. Unlike the product campaign, the fallback's later slots do not require a confirmed earlier slot; any uncertain local publication attempt still blocks subsequent fallback posts. Existing daily caps, official duplicate checks and the product PR quality gate remain unchanged.

After review, merge and deployment, enable locally with `node --env-file=.env src/activate-threads-daily-cycle.js --activate-fallback`. This requires the existing owner policy and a healthy updated core. No publication is performed by activation. The next Daily Commander creates a fallback if research fails. A same-day research-only hold can be replaced by rerunning Daily Commander only when no local attempt or approval exists; existing publishable plans remain immutable. Missed slots are not replayed. `--pause` disables the local policy. `/health` reports `editorialFallbackEnabled`.

The resilience extension adds a fixed 17:30–18:00 JST retry window for fallback days and a 23:15–23:45 JST stock research window. Each is reserved once per date on disk, including across restarts; each research pass is limited to six item detail attempts, respects the shared 429 cooldown, and never submits posts. Store at most twelve qualified candidate leads for seven days; current official item identity/name and literal evidence must be retrieved again before a stock candidate can be used. The morning commander prefers these leads. At 19:30 an evening retry may replace only the unattempted final fallback slot, and only if both morning and lunch guides were confirmed, the theme and original fallback digest match, and the full unchanged product auto-policy gate passes. Otherwise the non-commercial evening guide remains. No earlier slot is replayed. The nightly evaluation recognizes the actual confirmed evening PR.

Local anomaly detection records `EDITORIAL_ATTENTION` once per changed alert state, writes `.data/editorial-alert.json`, and exposes stock count, research result and alert via `/health` (`editorialResilience`) and the nightly report. No external notification destination is configured or enabled. The research feature is controlled by the same explicit `--activate-fallback` opt-in; no change to external reply authorization. Verify the matching GitHub revision, run the full repo CI and test on M8 before production activation. The partial development snapshot does not contain every repository dependency, so local unit tests do not constitute a Windows integration test.
